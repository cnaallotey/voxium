# Voxium

Keep developers and coding agents inside your architecture.

Voxium infers or defines your architecture, writes it to `voxium/architecture.json`, gives agents the rules (CLAUDE.md, AGENTS.md), and blocks pull requests that violate it.

See SPEC.md for the full product spec.

## Packages

* `packages/core` (`@voxium/core`): import graph, rule checker, inference, generators. Shared by the CLI and the future platform.
* `packages/cli` (`voxium`): the command line and the local MCP server.
* `packages/platform` (`@voxium/platform`): Next.js on Cloudflare Workers (OpenNext). GitHub sign in, GitHub App webhooks, repo analysis, setup pull requests, PR status checks, D1 for results.

## Try it

    npm install
    npm run build
    npm test
    node packages/cli/dist/cli.js init --root /path/to/a/ts/project
    node packages/cli/dist/cli.js check --root /path/to/a/ts/project
    node packages/cli/smoke-mcp.mjs /path/to/an/initialised/project   # MCP end to end test

## Platform setup

1. Create the GitHub App with the manifest helper in `packages/platform/github-app/` (see its README for the full walkthrough, including the end to end test steps).
2. `cd packages/platform`, copy `.dev.vars.example` to `.dev.vars` and fill it in.
3. `npx wrangler d1 create voxium`, put the id in `wrangler.jsonc`, then `npm run db:migrate:local`.
4. `npm run cf:preview` to run it locally in the Workers runtime. `npm run cf:deploy` to deploy.
5. Production secrets: `wrangler secret put GITHUB_APP_PRIVATE_KEY` (and GITHUB_CLIENT_SECRET, GITHUB_WEBHOOK_SECRET, SESSION_SECRET).

How it works: the repo holds the rules (`voxium/architecture.json`). The platform reads the repo tarball in memory, never stores source, and writes results to D1. Pull requests are judged by the rules on the BASE branch, so a PR cannot weaken the rules it is checked against. Setup opens a PR after a person reviewed what was inferred, it never pushes to the default branch.

## Reviewing the setup

* **Set up Voxium** on the dashboard infers an architecture from the default branch and stores it as a draft (module names, globs, rule ids, counts and notes, never the contents of a file), then opens the review page. Nothing is written to the repository yet. A repository with code that cannot be read and that the check depends on gets no draft, as before.
* The review page shows each module with the files it matches, each layer with the share of the imports between it and the other layers that go down the order, each rule with the violations it finds now, and the notes, among them the frameworks the root `package.json` uses (Next.js, Nuxt, Express, NestJS, Vite). It is a plain form without scripts: keep or reject a module, rename it, change its globs (one a line, starting with a folder name, so that none takes in every file), number the layers, switch rules off or make them `warn`, and edit what is not checked. Fields are named by position and the form is read strictly: a field the page does not send, a field sent twice, a value it does not offer or a body over 256 KB is refused, so a form cannot add rules, exceptions or anything else. A glob the edits add (to `ignore` or to a module's paths) may have at most 16 wildcards and may not be listed twice in one list, and together the added globs are held to a budget, checked before any file is matched, so that nobody who may send the editor can keep the server busy with long globs full of wildcards. A glob counts each time it is listed (in `ignore` and in each module that has it): for each file; for each character of its start and its end (the text before its first wildcard and after its last) when a file is long enough to be compared with them; when it has plain text in the middle to look for (of which the first 16 characters are looked for), for each character of a file after the start, and more for each character of the file that this text has too, since searching compares at nearly every one of those; and for each character of the files it has to be followed through. A file whose start or end rules a glob out costs little. On 9,000 files of about 45 characters that leaves room for about 40 globs such as `**/*.generated.ts` or `**/__tests__/**` when a tenth of the files have such names, hundreds that name a folder such as `src/legacy/**`, or about ten that every file has to be followed through, such as `src/**/*.ts`. In tests on a four-core machine, globs at the full budget took 0.3 to 0.6 s of CPU to apply, and the setup and the checks of later pull requests, which read each glob once and not once for each file, about half that. That holds for paths of about 1,000 characters too, also with starts of 250 to 480 characters, plain text of hundreds of characters, or plain text that nearly matches at every character of a path, the slowest shape found (1.0 s to apply, 0.5 s to check). Globs the draft or the current rules have already are not held to it, as often as they list them.
* **Open the setup pull request** reads the tip of the default branch again, applies the edits to the draft and works out the baseline from that tip, so commits made since the draft count. If rules were added to the default branch meanwhile, nothing is changed and the repository is marked as set up. An edit that would leave no file in any module (such as ignoring `**`) is refused. Warnings (a module with no files, an ignored glob that leaves out more than half of the files or matches anywhere) are shown first and need a confirmation that covers exactly the warnings shown. Refused and warned edits are kept with the draft and shown again. The pull request is written on top of the commit the baseline was worked out on, never on a newer one. When GitHub fails to open it, the draft is left as it was, so the page does not claim a pull request was opened and the same form can be sent again.
* A form for a draft that changed since the page was shown is refused, and of two people who send the same draft only the first opens the pull request; the other sees who did. Sending it again later replaces the files in that pull request. **Infer again** replaces the draft.
* The pull request says how many parts of the draft were accepted, edited and rejected, and so does a `setup_reviewed` entry in the audit log. Names from the repository are shown in it as code or plain text.
* The draft, its page and the pull request are for Owners and Team Leaders with write access, confirmed with GitHub at that moment. The same editor is on the **Proposals** page (**Edit architecture** on the repo page of a repository that is set up), where it makes a proposal from the rules on the default branch.

## Keeping the generated files up to date

* The setup pull request names the organization's current Owners and Team Leaders in `voxium/CODEOWNERS.suggested`, by their GitHub logins (only real logins or `org/team` names, so a name cannot add lines of its own).
* **Regenerate files** on the repo page (for an Owner or Team Leader with write access, confirmed with GitHub at that moment) opens a pull request on the branch `voxium/sync` with the generated files that differ from what the rules on the default branch give: the agent rules (only their Voxium block changes), the Cursor rules, the suggested CODEOWNERS, and the workflow, GitLab job, hook and `.mcp.json` for the version the workflow pins. It never rewrites `voxium/architecture.json` or `voxium/baseline.json`. Sending it again replaces that branch. Since it brings the blocks up to date it needs no approval, unless it changes the workflow or the GitLab job. After a merged change to the rules, the decision log links to it.

## What stops a PR from getting around the rules

* A PR that changes `voxium/architecture.json`, `voxium/baseline.json` or `.github/workflows/voxium.yml` fails `voxium/rules` until an Owner or Team Leader with write access approves that exact commit in a GitHub review. It is then judged by the rules they approved. A solo owner can approve their own pull request in Voxium instead (see below). If the rules on the base branch changed meanwhile, the branch has to be updated first. Removing baseline debt needs no approval.
* `voxium/rules` is only ever written by a check against the default branch. PRs into another branch report as `voxium/rules (branch name)`. Require that name if you protect the branch.
* Files outside every module are followed: importing one counts as importing everything it leads to.
* Committed files are not skipped because of their folder name. List build output in `ignore` in the architecture file. Ignored files are not judged themselves, but importing one still counts as importing what it leads to.
* Every file is compared with its git hash, so `.gitattributes` cannot show the check something else than what is committed. If a source file or a config file that says what imports stand for (see below) cannot be read as committed (over 4 MB, over the 40 MB total, symlinked, or changed by `.gitattributes`), the check is an error, not a pass. Ignored files are exempt as long as no checked code leads to them.
* The code is parsed with `@babel/parser`, so what looks like a comment or a string cannot hide an import. Code that may run as a module or as a script is parsed as both where they can differ, and what either of them imports counts. A file that does not parse, is larger than 1.1 million characters (a `.vue` file as a whole), is nested too deeply or takes the parser too long counts as one that could not be read. How deep is too deep is measured on the parsed code, by about the stack the parser needs for it (around 200 nested calls or brackets, or 2,000 operators in one chain), so the same file gets the same answer every time, and so does a `.vue` file of which it is not certain where a `<script>` ends or what its `lang` or `src` is. It is never a pass: fix the file, or ignore it if it is not source.
* When several checks of one commit overlap, only the newest one reports.
* The Voxium block in `CLAUDE.md`, `AGENTS.md` and `.cursor/rules/voxium.mdc` (between `<!-- voxium:start -->` and `<!-- voxium:end -->`) tells coding agents the rules, so a PR that edits it, removes it (also by deleting the file), adds a second block, or moves it into a code fence or an HTML comment needs the same approval of its exact commit as a change to the rules, and is named as such. Markers in another case or width, with invisible characters or accents count as markers. In the Cursor file the frontmatter before the block counts too, since it decides whether Cursor reads it. Text outside the block is never a change to it, and neither is a block that is out of date because the rules changed since and nobody regenerated it, as long as the PR leaves it alone. The block is compared with the one the rules the PR is judged by give, and only a file whose block differs from that is compared with where the PR branched off; the agent files come from the archive the check reads anyway.
* `voxium/gitlab-ci.yml` is protected like the workflow.

Repository settings that this depends on: require the `voxium/rules` status **with the Voxium app as its source** (otherwise anyone who can push can post that status), require branches to be up to date, and put `voxium/CODEOWNERS.suggested` in `.github/CODEOWNERS` with code owner review required.

## Running the CLI from npm

Generated files never tell a machine to run an unpinned package. `.github/workflows/voxium.yml`, the `.mcp.json` entry and the `npx` line in the agent rules are only written when you name an exact published version, such as `voxium@1.2.3`: set `VOXIUM_CLI_PACKAGE` for the platform, or pass `--cli-package` to `init` and `generate`. Leave it empty until the CLI is on npm under an account you control. Anyone can register a name that is not taken, and those files would run their code. The `voxium/rules` status does not use npm.

That GitHub Actions job uses the rules from the default branch, but a PR can still edit workflow files. Without the platform, CODEOWNERS review is what protects them.

With a pinned version, Voxium also writes `voxium/gitlab-ci.yml`, a job for merge requests to include from your `.gitlab-ci.yml` (`include: - local: voxium/gitlab-ci.yml`; Voxium never edits `.gitlab-ci.yml` itself). It fetches the default branch by its full ref, takes the rules from it, and runs the CLI from an empty folder, so that a `voxium` or an `.npmrc` the merge request ships is not used. GitLab runs the CI config of the merge request's own branch, so a merge request can edit both files: require pipelines to succeed and have a Team Leader own them. It has not been run on GitLab. It also writes `voxium/hooks/pre-commit`, which runs `check --staged` the same way. Nothing installs it: copy it to `.git/hooks/pre-commit` and make it executable, rather than pointing `core.hooksPath` at it, so that a pull request that edits it runs nothing on your machine.

## Who can see and do what

GitHub decides, and the platform never grants more than GitHub would.

* Owner is an admin of the GitHub organization, or the account holder of a personal account. Nobody becomes Owner by signing in first.
* Roles and the list of repos are refreshed from GitHub at every sign in. Sessions last 8 hours. "Refresh access" on the dashboard does it sooner. Losing sight of an organization (suspended app, no SSO session) takes access away but keeps a Team Leader's role for when it returns. Leaving the organization ends it.
* Opening a repo page, drafting, reviewing or opening the setup and counting an approval each ask GitHub again at that moment. If GitHub cannot answer, access is refused.

## Organization rules

* **Organization rules** (on the dashboard, for Owners and Team Leaders as GitHub confirms them at that moment) holds one rule set for the organization, saved as a new version each time with a reason, never changed afterwards, and audited. Its rules are those that mean the same in every repository: `deny_external` and `naming` for every module (`"*"`), `max_file_lines`, `no_cycles`, `no_opaque_imports`, and `placement` where every module it names exists. `layers` and `deny_dependency` are refused, since module names differ from repo to repo. Ids start with `ORG-`, a set has at most 20 rules, and their text is one line (at most 500 characters of description and 2,000 of rationale), because it goes into the agent rules of every repository. **Check and preview** validates the rules and shows what the next version changes; **Save** saves what was previewed, only when nobody saved a version meanwhile, so two people saving at once never get the same version.
* Saving a version changes no repository. The page lists the repositories you can open, with the version each has (from its newest analysis) and its overrides. **Open update pull request** makes a proposal, with you as the one who asked: on its page, its pull request is opened like any proposal's, lists what would newly fail, and can accept that as debt. It is approved in Voxium by an Owner or Team Leader other than you, or on the solo path. The rules are written into the repository's `voxium/architecture.json`, each marked `"org": { "version": n }` after the repository's own rules, with `meta.orgRules` naming the set; applying a version again changes nothing, and an update replaces the rules in place, removes those the set no longer has with their overrides, and keeps the repository's own rules, layers, exceptions, ids and the order of keys. A repository whose own rule has the id of an organization rule, or that lacks a module a placement rule names, is refused. A module in `except` that the repository does not have is left out there. Checks only ever read the repository's file, so the CLI and CI enforce what was merged without the platform.
* A repository can override an organization rule in `overrides`: `{ "rule", "action": "disable" | "warn", "owner", "reason", "expires" }`, at most 15, one a rule, only for rules marked `org` (and only types that can be organization rules can be marked). It is a change to the rules like any other, so it needs approval. Until it expires the rule is off or a warning there; after that day the rule is enforced again, and the expired override fails checks like an expired exception until it is renewed or removed. The agent rules say so next to the rule. In what a Team Leader approves, adding, removing or changing an organization rule, marking a rule as one, and every override are each a line of their own, put before everything else and never left out however large the change.
* The repo page says which version a repository has, when it is behind the set, and its overrides with their expiry.

## Drift, the diagram and the audit log

* After every pull request merged into the default branch, and when an Owner or Team Leader with write access presses **Analyse now** on the drift page, Voxium analyses the tip of the default branch by its own rules and keeps a snapshot: how many files each module has, the imports between modules and how many of them the rules forbid, the violations of each rule as new, accepted debt, excepted or warnings, and the exceptions with their expiry. A snapshot holds no code and no violation message, and at most 200 KB (the imports the rules forbid are kept first). A repo is analysed at most once a minute, however many merges or clicks there are; a later merge is seen by the next run. When some code could not be read, the snapshot is marked incomplete and left out of the trend, never shown as zero. The same commit is one snapshot, and snapshots are ordered by when their run started, so a run that finishes late does not pass for newer data. A repo keeps its newest 400 snapshots and 500 pull request checks; nothing else is pruned. Analysing never changes a status.
* **Drift history** (on the repo page) shows the trend of accepted debt and new violations as a picture and a table, the debt by rule and by module, the exceptions by expiry, and how many pull requests a check blocked each week.
* **Diagram** shows the modules with the layers as rows and the imports between them; the imports the rules forbid are red, thick, dashed and counted, so they do not depend on colour. `?module=` shows only one module's imports, and the table below has the same as text. Above 60 modules only the table is shown.
* **Overview** (on the dashboard) shows, for each repository of the organization that you can open, its debt, its new violations, the exceptions that ran out or run out within 14 days, and when a pull request was last checked. Nothing is added up across repositories.
* **Audit log** (on the dashboard, for Owners as GitHub confirms them at that moment) lists who did what, newest first, 50 to a page, and can be filtered by action and exported as CSV or JSON (up to 10,000 entries). The export is logged too. In CSV every cell is quoted, and one that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a `'` in front, so a spreadsheet reads it as text. Sign ins, role and Team Leader changes, setup, proposals, approvals, regenerating and analysing are logged.

## Comments on pull requests

When a check does not pass, Voxium explains it on the pull request: one summary comment, edited in place, that also lists new warnings as not blocking, and a comment on each new violating import that is part of the diff (up to 20 at a time), with the rule, the reason and a suggested fix. When a violation is gone its comment says so. A pull request that passes from the start gets no comment. Comments people delete stay deleted, except that the summary returns when a check fails again. Comments never approve or block, and trouble with them never changes the `voxium/rules` status.

## Approving changes to the rules

The `voxium/rules` status links to the pull request's page in Voxium, which says in plain words what the change does to the rules.

* Usually an Owner or Team Leader approves with a GitHub review. An organization's Owners choose Team Leaders on the People page, linked from the dashboard.
* GitHub does not let anyone approve their own pull request. Someone who is the only member of their organization, or the holder of a personal account, can do it on that page with a written reason. It covers one commit into one base branch. It stops counting when they lose ownership or write access, or when someone joins the organization.
* Approving takes a signed in browser session on Voxium, so a GitHub token, such as one a coding agent uses, cannot do it.
* Every merged change to the rules is in the decision log on the repo page: what changed, who asked for it (for a proposal), who approved it and why. Changes that were merged without approval are in it too. **Add to the repository** opens a pull request with the log as files in `voxium/decisions`.

## Proposals

Nobody has to edit JSON by hand to change the rules.

* Anyone who can open a repository on Voxium can propose, on its **Proposals** page (a plain form of at most 256 KB): an exception to one rule, accepting the violations on the default branch that are not accepted yet, or an edited `voxium/architecture.json`. The page says in plain words what the proposal does to the rules as they are now.
* Agents call `propose_architecture_change` on the MCP server, and people can run `voxium propose`. Both write a file to `voxium/proposals/` (a second one with the same title on the same day gets a number, never replacing the first). When a pull request into the default branch adds or changes such files, the check imports them for the platform, at most 20 of 64 KB each, only if the pull request's author can write to the repository. Its author counts as the one who asked, and so does everyone GitHub names as the author or committer of a commit in the pull request, because any of them may have put the file there. When GitHub cannot name them all (a commit whose email matches no account, or 100 commits or more), nothing is imported. The same file imported twice is one proposal, files that are not valid proposals are left out, the status or approver a file claims is ignored, and importing never changes the check's verdict.
* An Owner or Team Leader with write access turns a proposal into a pull request that Voxium writes on a new branch `voxium/proposal-<id>` (a branch of that name that exists already is refused, never reused). Voxium checks the default branch under the new rules and under the current ones first, and writes its commit on top of the commit it checked, so nothing merged meanwhile is undone. A violation is new when it fails under the new rules and not under the current ones. When the proposal accepts debt, exactly those are added to `voxium/baseline.json`, and the pull request lists each of them. Violations that already fail under the current rules were not made by the change, so a change to the rules never accepts them: the pull request lists them as already failing. They are matched by the code they are about, not by their ids, so renaming a rule or a module, or moving an import from the layers to a dependency rule or a cycle, does not make them new. A `public_api` import through a file outside every module is matched by the importing file and that outside file, so neither renaming the module nor adding or removing entries (which turns one violation for the whole module into one per file, or back) makes it new; in exchange, a new violation of such an import that already fails is listed as already failing rather than accepted. Debt already accepted on the default branch does count as new under a new id, so a proposal that accepts debt carries it over. Only a proposal that keeps the rules and accepts the debt accepts what fails now. An exception's rule, file, owner and reason, including those of every exception in a proposed architecture, are kept on one line without invisible characters, and lists, rules or heading underlines in what people wrote stay text in the pull request. CLAUDE.md and AGENTS.md are regenerated with the new rules. A proposal that replaces the whole architecture is refused once the rules on the default branch changed since it was written, so it cannot undo someone else's change. Rejecting a proposal takes a written reason and is in the audit log.
* GitHub reviews do not count for these pull requests, because their author is Voxium: anyone holding a Team Leader's GitHub token could submit one. They are approved on the pull request's page in Voxium, with a reason, for one exact commit into the default branch, by an Owner or Team Leader GitHub confirms at that moment, with write access. The approval counts only while `voxium/architecture.json`, `voxium/baseline.json` and the workflow at the head are exactly what Voxium wrote: once a commit on the branch changes them, even a merge from the default branch, nobody can approve it, and the proposal has to be made again. Whoever asked for the change cannot approve it unless they are alone in the organization, as for approving your own pull request. Neither can anyone through a branch named `voxium/proposal-<id>` that Voxium has not recorded as a proposal's.
* Merging or closing the pull request decides the proposal, and the decision log names who asked. Reopening a closed one makes the proposal open again, and a merge always counts.

## Commands

* `init`: infer an architecture, write it with a baseline and agent rules (`CLAUDE.md`, `AGENTS.md`, `.cursor/rules/voxium.mdc`, which Cursor reads in every chat) and `voxium/CODEOWNERS.suggested`. `--cli-package <name@version>` adds the CI workflow, the GitLab job, the pre-commit hook and `.mcp.json`. `--with-tests` adds `voxium/dependency-cruiser.json`: `forbidden` rules for `layers`, `deny_dependency` and `deny_external`, and file-level `circular` for `no_cycles` (stricter than Voxium's cycles between modules), for `depcruise --config voxium/dependency-cruiser.json` from the repository root. It does not see imports through files outside every module, the baseline or exceptions, so `voxium check` stays authoritative. It has not been run against dependency-cruiser itself; its regular expressions are tested against Voxium's globs. `--template <name>` starts from a template instead of the inferred modules: `layered`, `hexagonal`, `feature_sliced`, `modular_monolith`, `next` or `nuxt`. Only the template's modules that match at least one file are written, each with the default rules plus the ones the template is known for (an index file as the public API of each Feature-Sliced slice and of each module of a modular monolith, no server code in the client modules of Nuxt), every rule with its rationale. Ignored paths and aliases are worked out from the code either way. The modules of a modular monolith start in alphabetical order: put each above the modules it may use. A folder of a modular monolith named with `*` or `?` is left out, since its glob would take in the folders next to it, and two folders that would get the same module name get distinct ones.
* `infer`: print the inferred architecture only, with how sure inference is of each module, layer and rule, and the frameworks the root `package.json` uses.
* `check`: exit 1 on new blocking violations, 2 when some of the code, or a config file above it, could not be read to its end and is not ignored. `--update-baseline` refuses to write in that case. Formats: text, json, github. `--rules-from <ref>` takes the rules and baseline from a git ref instead of the working tree, and warns when the change alters a Voxium block. `--staged` checks what git has staged, as the next commit would hold it (ls-files and cat-file, so unstaged fixes and unstaged breakage do not count, renames do), by the rules and baseline of `HEAD`, so staging weaker rules does not help; before the first commit, by the staged rules. `--changed <ref>` analyses the whole project but shows only violations in files changed since where `HEAD` branched off from the ref (untracked ones included) and in the files that import them: quick feedback while working, not for CI. Git runs with fsmonitor off, and without external diff or textconv. These options cannot be combined with each other or with `--update-baseline`.
* `generate`: regenerate agent rules from the architecture file, and the workflow, GitLab job, hook and `.mcp.json` when the workflow or GitLab job already pins a version or `--cli-package` gives one, and the dependency-cruiser rules once they are there. A `voxium/CODEOWNERS.suggested` that is there is kept, since the owners in it may have been filled in. Nothing is written through a symlink that leads out of the project.
* `mcp`: run the MCP server over stdio. Tools: `get_architecture`, `get_rules_for_path`, `check_import`, `check_change`, `propose_architecture_change` (with an optional whole architecture or one exception, and `acceptDebt`).
* `propose --title <t> --summary <s> --rationale <r> [--architecture <file>] [--accept-debt]`: save a proposal in `voxium/proposals/` for the platform to import from a pull request (see Proposals). It refuses an invalid architecture and never replaces an existing file, also not through a symlinked folder.

## Rule types

`layers`, `no_cycles`, `deny_dependency`, `deny_external`, `max_file_lines`, `no_opaque_imports`, and the conventions `naming`, `placement` and `public_api`. Exceptions need an owner, reason and expiry date. Every `layers` rule is enforced, not only the first.

```json
{ "id": "NAME01", "type": "naming", "module": "*", "files": "src/**", "style": "kebab", "ignoreSuffixes": ["_test"], "severity": "warn", "description": "...", "rationale": "..." }
{ "id": "PLACE01", "type": "placement", "files": "**/*.repo.ts", "modules": ["data"], "severity": "block", "description": "...", "rationale": "..." }
{ "id": "API01", "type": "public_api", "module": "data", "entries": ["src/data/index.ts"], "severity": "block", "description": "...", "rationale": "..." }
{ "id": "EXT02", "type": "deny_external", "module": "*", "except": ["data"], "packages": ["pg"], "severity": "block", "description": "...", "rationale": "..." }
```

* `naming`: the source files matching `files`, in `module` or with `"*"` in every file (also those outside the modules), have names in one style: `kebab`, `camel`, `pascal` or `snake`. There are no user regexes. The part of the name before the first dot is judged (`UserCard.test.ts` is `UserCard`, `.eslintrc.cjs` is `eslintrc`), with the endings in `ignoreSuffixes` (letters, digits, `-` and `_`) left out. Styles take ASCII letters and digits only, so a letter that only looks like one does not pass. `index`, route parameters such as `[id]` and `[...slug]`, `$id`, and `_app`, `_document`, `_error`, `_middleware`, `+page`, `+layout`, `+server`, `+error` are skipped. In a folder called `routes`, Remix flat route markers are read as Remix reads them: a leading `_` (pathless layouts such as `_auth.login.tsx`, and `_index.tsx`) and a trailing `_` (`concerts_.mine.tsx`) are left out, an optional segment in parentheses is judged without them (`(en).about.tsx` is `en`) or skipped when it is a parameter (`($lang)._index.tsx`), and a dot in square brackets does not end the name while what is in square brackets is left out (`sitemap[.]xml.tsx` is `sitemapxml`). Elsewhere these characters are part of the name. The violation id is `<rule>:<file>`, so a rename, also one that only changes case, is a new violation.
* `placement`: every source file matching `files` is in one of `modules`. A file outside every module breaks it too. The id is `<rule>:<file>`.
* `public_api`: another module may only import the files of `module` that match one of `entries` (at most 20 globs, one such rule per module). Imports through files outside the modules count, for every file of the module they reach: a barrel outside the modules that re-exports an entry and an internal file is reported for the internal file. The id is `<rule>:<from>-><to>`, or `<rule>:<from>-><via>=><to>` through a file outside the modules. An import through such a file that reaches more than 20 internal files is one violation instead, with the id `<rule>:<from>-><via>=><module>` and a message that says how many files it reaches, so that a barrel of hundreds of files imported by hundreds of others gives one violation per import and not one per pair. Which files there are never decides which ids exist: deleting a file, or making one an entry, never brings up a new id, and the per-file violations of an import are also accepted by its whole-module id in the baseline, so coming down to 20 files or fewer does not fail either. Past 20 files, though, a new internal file reached through the same import and outside file is part of the violation already accepted, as with `layers` through a file outside the modules; another file importing that barrel is a new violation. A package that resolves to its `package.json` (its `main` is build output that is not in the tree) is an entry only when that `package.json` is listed.
* `deny_external` with `"module": "*"` applies to every module but those in `except`.
* Files in `ignore` are skipped by `naming` and `placement`, unless code that is checked imports them, as with files that cannot be read.
* At most 30 `naming` and `placement` rules together, and globs of at most 512 characters. Matching a glob against a path takes at most their two lengths multiplied, so a check grows with the number of files and no faster, but these limits alone do not keep every check within the platform's CPU time: in a test, 30 rules with 512-character globs written to match slowly took about 20 s of CPU for 1,000 files with 130-character paths. Such rules can only come from the base branch or an approved change, and the `paths` of modules and `ignore` cost the same per glob. Module names come from `modules` only (`"*"` cannot be one), `modules` and `except` hold at most 50 of them, each once, and lists must hold strings.

Rules with severity `warn` never fail a check, change the `voxium/rules` status or its description, or change the CLI's exit code. The CLI prints them as `WARN`, all of them. On the platform, new ones (up to 50, with the count of all) are listed on the pull request's page and in the summary comment under "Warnings, not blocking", without comments on the lines. New means not in the baseline, not covered by an exception, and not there where the pull request branched off under the same rules, so warnings the repository already had are not listed on every pull request. To tell, a check with warnings also reads the code where the pull request branched off, downloading that commit when the pull request changes or removes a source or config file, after the status is published. Only the rules with severity `warn` are checked there, with every path of that commit as for the head (files that could not be read count as there, and paths that are not source code, such as a data file an opaque import names or a committed `node_modules`, are seen), and the files the pull request does not change are not parsed again, so on a 9,000-file repository this adds about a quarter to the check (measured: 380 to 430 ms for the check, 100 to 120 ms more for the warnings). When that code cannot be read, the status stays as it is and the page and comment say that the warnings could not be worked out, instead of listing any. A pull request that passes with only warnings still gets no comment. A change from `block` to `warn` is one of the changes to the rules that needs approval, and it is named as such. The description of a change to the rules has at most 60 lines. When there are more, the items of the lists of new rules and the items a list no longer has are left out first, then the items a list now has when there are more than three (those are also said together in one line, which is kept and names how many have wildcards and the three that can take in the most: for the entries of a `public_api` rule, those that match more of a few files made up from the module's own paths (`index.ts`, `lib/util.ts`, `a/b/c.js`, `x.vue` and others in place of their wildcards) go first, then those with a wildcard, then the less that comes before it, so an entry such as `src/**` that takes in the whole module is named wherever it was put, unless three others take in as much, and entries that only start with a wildcard, such as `*x`, cannot push it out; past a bound on that work in one description, which honest rules do not reach, the rest are ranked by their text alone), then other lines, and a lower severity, a removed rule, module or alias, a rule whose type, `files` or other settings change (not only its description or rationale), one to three items a list of a rule now has (an entry, a module it allows or leaves out, an ending), a module whose paths change, a new module placed before modules that exist (which can take their files; more than three of them are also said together in one line), the layers or the modules in another order, an exception, an ignored path and accepted debt last, so these are shown before anything else, also before any number of added modules. `ignoreSuffixes`, `entries`, `modules` and `except` may not name the same item twice.

The agent rules list the conventions in words, and `get_rules_for_path` gives the naming style, the modules a file like it belongs in and the entries of the modules it may import; `check_import` refuses a file that is not an entry and names the entries to use instead. Rule text in the agent rules is kept on one line, and comment markers in it are broken up, so it cannot end the managed block early or start another; anything that reads as a marker in another case, width or with invisible characters is broken up too. Rule text never reaches the GitLab job, the hook or a regular expression of the dependency-cruiser rules.

Architecture files with the convention rules, `except` or a second `layers` rule need a CLI and platform from this version on: older ones read the new rule types as an invalid file, which is an error, never a pass. An older CLI ignores `overrides` and the `org` marks, so it enforces the organization rules that overrides turn off: stricter, never weaker.

A cycle is reported at the import that causes it, with the imports that lead back: the one the change adds when that is known (on a pull request and in `check_change`), otherwise one that goes against the layer order. An exception to a `no_cycles` rule is about the imports in the files it names. The cycle is excepted when, without those imports, no cycle is left that is not accepted debt.

When a change removes part of a cycle that is accepted debt, what is left of it is accepted too, as long as no module in it got a connection to another that was not there before. "Before" is where the pull request branched off, or with `check` alone the last commit. Where that cannot be read, a smaller cycle counts as new. The baseline does not have to be updated for this; `--update-baseline` narrows it to what is left, which like any addition to the baseline needs approval.

## What counts as an import

* `import` and `export ... from` in every form, also with string names, attributes, types only or `import x = require()`.
* `import()`, `require()`, `require.resolve()`, `import.meta.resolve()` and `new URL("./a", import.meta.url)`, when the name is a string, or strings that are added together or put into a template literal. Code inside `${}` counts, and so do escapes such as `"\x2e/a"`. A cast does not change what a name is.
* The same for what `createRequire(import.meta.url)` returns, or `createRequire(__filename)` in a CommonJS file (`.cjs`, or `.cts` also with import syntax, which TypeScript compiles to CommonJS), when it is called directly or declared under a name, as in `const load = createRequire(import.meta.url)`. Names go by their scope, and the two scripts of a `.vue` file share theirs.
* `` import(`./pages/${name}`) ``, the same in `new URL`, `import.meta.glob` and `require.context` count as importing every project file they can match, up to 1,000 per call.
* A name that Node or a bundler reads as a URL: `./%61`, `.\a` and `./a?raw` all import `./a`. A query is also left off a package name, so `lodash?x` is `lodash`.
* In `.vue` files, the code of every `<script>` and `<script src>`, the expressions of the template (`{{ }}`, and the values and dynamic arguments of `v-`, `:`, `@`, `#` and `.` attributes) and what `v-bind()` has in a `<style>`, which Vue compiles into the same module and which see the names of `<script setup>`. A template expression that cannot be read, a character reference in one that is not known, or a template in another language such as Pug is opaque when it mentions `import` or `require`. When too many of them cannot be read, or one is nested too deeply, the file is unparsed. `<template src>` is opaque, because the file it names is not read. What another block only shows, such as an example in `<docs>`, or what is in an element with `v-pre` (in lower case: Vue compiles what is in `V-PRE` or `v-Pre`), does not count, unless it is not certain where that block or element ends.
* A relative or alias import of a file in the tree that is not a source file, such as `require('./x.txt')`, `require('./x')` of a file without an ending or `import './x.d.ts'`, is opaque, because Node runs it as code. That includes such a file found with an ending added, as the `index` of a folder or as what a folder's `package.json` names in `main`, a file in a committed `node_modules` folder, as in `require('./node_modules/x')`, and a bare `require('x')` that Node finds in a committed `node_modules` folder of the importing file's folder or one above it (the package edge stays as well). The file Node loads is judged in Node's order: a file of that very name comes before one with an ending, so `require('./x')` next to both `x` and `x.js` loads `x`. A symlink is judged by what it points to: `q.cjs` pointing to a `.txt` file is code, and `config` pointing to `config.json` is data. The same holds for what config files resolve a name to: what tsconfig `paths` or `baseUrl`, an alias of the architecture, `package.json` `imports`, or a workspace package's `exports`, `main`, `module`, `types` or subpath names, by its very name (as Node loads it), or with an ending or as a folder when no source file is there, as with `"#s": "./src/secret.txt"`. A relative import of a folder whose `package.json` is in the tree but not read, as in a committed `node_modules` folder, or cannot be read (not valid JSON, larger than 1 MB), is opaque whatever `index` the folder has, because Node reads `main` first and it may name anything; one outside `node_modules` that cannot be read also makes the check incomplete. A declaration file is only taken for types where config names it for TypeScript: tsconfig `paths` and `baseUrl`, the `types` and `typings` fields and a `types` condition. One that `imports`, `exports`, `main` or `module` names otherwise, as in `"#lib": "./lib.d.ts"`, is opaque, since Node runs it. So is a name with unknown parts or a `require.context` that can match such a file, as in ``require(`./${name}.txt`)``. Data and assets (`.json`, styles, images, fonts, media, `.html`, `.md`, `.yaml` and the like, or `?raw` and `?url`) are not. The CLI and the platform know every path of the tree, symlinks included. The MCP tools only know the source files, so there it is not seen.

Anything else that is done with `require`, `createRequire` or `node:module` so that a module could be loaded with it is opaque, because the check does not trace values: `import(name)`, `const load = require`, an export or a property that holds one of them, `createRequire` for another folder (also `createRequire(__filename)` after `var __filename = ...`, and in a module or in a `.js`, `.ts` or `.vue` file that may be one, where `__filename` is a global that any other module can set), `module.parent.require()`, writing what `node:module` has (`Module._resolveFilename = ...`, `Module.wrap = ...`) or what decides where `require` looks (`module.filename`, `module.paths`, `module.id`, also through `require.main`, `require.cache` or `Object.assign(module, ...)`; any use of `module.paths` other than its `length`, a test of it or `===` counts, also `console.log(module.paths)` or `module.paths.join()`, because callbacks of `forEach` and `map`, and whatever is put into `Array.prototype`, are given the array itself), any property of `require`, of what `createRequire` made or of a CommonJS module object that is not known to hold only data (`require.valueOf()`, `module.children.forEach()`), `process.getBuiltinModule()`, `require.resolve()` with options, a `with` statement, or a module named by where it is on the disk (`file:` or `/app/x.js`). A `no_opaque_imports` rule reports that, once per file. `init` and setup propose it as a warning. Set it to `block` to keep such code out. A parameter or variable of your own that is called `require` is not opaque.

## How module names resolve

Config files only ever add to what an import stands for, never take something away, so a change to them cannot hide an import. Names resolve with the config files of the change and with those of the commit it started from, together: on the platform, where the pull request branched off; for `check --rules-from <ref>`, where `HEAD` branched off from the ref (or the ref itself when git cannot tell, as in a shallow clone); for a plain `check`, `HEAD`; and for `check_change`, the files before the planned change. So editing, emptying or removing any `tsconfig.json`, `package.json` or workspace file, not only the root ones, cannot take away what a name stood for. A name that is not relative keeps its package edge, so `deny_external` rules and their violation ids stay, and gets an edge to each file of the repo it can stand for:

* Relative names and `@/`, `~/`, `#/` (to `src` or the root) resolve as before, with endings and `index` added and `.js` standing for `.ts`. What Node's `require()` would load is added: the file of that very name first, then `.js`, `.json`, `.node` (and with type stripping `.cts`, `.ts`, `.mts`), then what the folder's `package.json` names in `main`, then its `index`. So `./x` next to both `x.ts` and `x.js` imports both. A name that ends with `/`, or whose last part is `.` or `..` (`../ui/`, `../ui/.`, `..`), stands for the folder only, as Node, TypeScript and bundlers take it: its `package.json` `main`, then its `index`, never a file of that name next to the folder. The same holds for such a name through `paths`, `baseUrl`, an alias or a workspace package's subpath.
* `tsconfig*.json` and `jsconfig*.json`: `baseUrl`, `paths` (the first target that is there, of the pattern that fits best, as TypeScript takes it) and relative `extends` within the repo, also several of them. Every such file in the importing file's folder or one above it counts, so a `tsconfig.json` in a folder can add mappings but not replace those of the root. `extends` of a package, of a path through a `node_modules` folder (as gts sets it up, `"extends": "./node_modules/gts/tsconfig-google.json"`) and of anything outside the repo is ignored, since `node_modules` is not read. So is an `extends` of a file that is not in the tree at all, as SvelteKit (`./.svelte-kit/tsconfig.json`) and Nuxt (`./.nuxt/tsconfig.json`) generate it and git ignores it; `init` and setup say so in a note. One of a file that is in the tree but not read is a gap.
* Workspace packages, by name: those that a `package.json` `workspaces` field (an array, or `{ "packages": [...] }` as Yarn has it), `pnpm-workspace.yaml` (its `packages` as a block list, indented or not, or a flow list on one or more lines, with or without quotes and comments) or `lerna.json` names, for the code in that folder, and `workspace:`, `file:`, `link:` and `portal:` dependencies, for the code below that `package.json`, or in the whole workspace when it belongs to a workspace package, since the package manager installs them for every member. A name resolves through `exports` (every condition, and patterns), or `main`, `module`, `types` and `typings`, then `src/index`. A file in `dist`, `build`, `out` or `lib` that is not in the repo stands for the same file in `src`. When nothing matches, the import leads to the package's `package.json`, which belongs to the package's module like its files. Two packages with the same name are both followed.
* `package.json` `imports` (`#db`) of every `package.json` above the file, under every condition (and every target of a fallback array), nested up to 32 deep. One that names a package, as in `"#db": "pg"`, also gives an edge to that package. A package may import itself by its name.
* An `npm:` alias (`"x": "npm:pg@8"`) gives an edge to the real package too, where that dependency is installed, also when it is in `overrides` (nested by package as npm has them, `"."` included), `resolutions` (`"**/x"`, `"a/x"`), `pnpm.overrides` (`"a>x"`), or the `overrides`, `catalog` and named `catalogs` of `pnpm-workspace.yaml` (as a block or a flow map; each map counts on its own, so an entry in one does not hide the same name in another). A Yarn `patch:` dependency stands for the package it wraps (`"x": "patch:pg@npm%3A8.11.0#./p.patch"` is `pg`). A dependency fetched from elsewhere stands for a package as well: a registry tarball URL for the package in its path, and another tarball, git or GitHub dependency for the last part of its path without an ending or version (`github:me/pg` is `pg`), which is only a guess, since the real name is in the package itself.
* `node:fs` is the package `fs`. A `deny_external` rule matches it written either way.
* `aliases` in `voxium/architecture.json`: names to repo relative paths, as tsconfig `paths` has them, such as `"@app/*": ["src/app/*"]`. `init` and setup write the paths and `baseUrl` of the root tsconfig and the packages of the root workspace into it, as far as the architecture can hold them (up to 1,000 names of up to 50 paths each, a `*` in a path only when its name has one, and no path that is the root of the repo itself); what is left out is named in a note. Like all rules they come from the base branch, so they keep these names when the config files change across several pull requests, and removing an alias needs approval. Each alias, and each path an alias no longer or now also stands for, is a line of its own in what a Team Leader approves. A long name or path is cut there with a hash of the whole, and shown whole when two would still read the same. Use them as well for aliases of vite, webpack or babel, whose config is code and is not run.

A config file that cannot be read (not valid JSON with comments, larger than 1 MB, more than 1,000 `paths` in one file or 5,000 in the whole repo, more than 20 tsconfig files in one folder or more than 50 with `paths` or `baseUrl` that apply to the same code, an `extends` that cannot be read or that goes round in a circle, `overrides` or `resolutions` nested more than 32 deep, a `packages` list in `pnpm-workspace.yaml` in another form than those above, `overrides`, a `catalog` or a named catalog there that is not a map of names to plain values (a key with a tag, an anchor or an escape counts as not plain), a top level there in another form than plain or quoted `key:` lines (a document that is a flow map such as `{packages: [...]}`, an indented document, a tag, anchor, alias, explicit `?` or merge `<<` key, a key written twice, or a second document), a line there longer than 16,384 characters, more than 1,000 workspace patterns or patterns times `package.json` files over 200,000, or not readable as committed) in the folder of some code or one above it makes the check incomplete, and so does one anywhere whose `exports` or `imports` nest more than 32 deep or have more than 1,000 entries where an import uses them, or whose mappings take more than 1,000,000 targets tried (matching a name against many patterns that begin alike counts too) or 400,000 different paths looked up, 400,000 different paths checked for code that is not read, or 30,000,000 characters of such paths together in one check (the file being used when that runs out is named). An honest repo with 40,000 different alias targets stays well within them; config made of very long targets reaches the character limit first. These limits keep a check within the platform's CPU time whatever config a pull request adds. It is as with code that cannot be read: an error on the platform and exit 2 for the CLI, unless the file is in `ignore`. Setup does not propose ignoring it, and refuses a repository with one, naming it as a config file with the reason. On the platform the check also lists the files where the pull request branched off (one more GitHub request), and downloads that commit only when the pull request changes a config file. When they cannot all be listed and read, the check is an error. Relative and alias imports that lead to no file, and names that a mapping was meant for but that lead to none, are counted as `unresolved` in the statistics of a check.

Earlier versions did not see all of these, so after an update a check can report violations that were there before and that the baseline does not list. They count as new. Fix them, or accept them with `check --update-baseline` in a pull request that a Team Leader approves.

## Known limits

* TypeScript, JavaScript and Vue files only. Syntax that only Babel plugins know is mostly not parsed, and Flow types only in files that say `@flow`.
* Module names do not resolve through `node_modules` (except that a committed one is opaque), Yarn Plug'n'Play, vite, webpack or babel config, or TypeScript project references other than tsconfig files in the folders above a file. A tsconfig `extends` must name a file called `tsconfig*.json` or `jsconfig*.json`, since only those are read, and a symlinked config file must point to a file named like a config file for the same reason (otherwise it is one that cannot be read). Packages are not resolved by `browser` fields or by the conditions a tool would pick: every condition counts. A committed `node_modules` folder, as GitHub Actions often have, makes every bare import that Node would find in it opaque, as a warning by default. Resolving has a limit per check (see How module names resolve): a repo with far more than 40,000 different alias targets, or 400,000 different paths to look up, is an error with "takes too many lookups" rather than a partial check. `pnpm-workspace.yaml` is read with a small YAML reader, not a full one: forms of YAML it does not read are an error, never no packages or no overrides.
* Inference proposes modules from top level folders and orders layers by import direction. Modules with no imports between them are ordered arbitrarily, so review the layers: the review page marks such a layer as a guess. The layer order is edited by number, without drag and drop. Templates are offered by the CLI only; the review page starts from the inference.
* A setup draft keeps the ignored unreadable files and the aliases of the commit it was inferred from. When the default branch gains code that cannot be read before the pull request is opened, opening it is refused until the architecture is inferred again.
* Proposals are decided on the platform only. Without it, a proposal file is just a file, and changing the rules takes a pull request that edits them, reviewed through CODEOWNERS. A proposal's pull request runs no tests of its own beyond the check, and someone with push access can still add code commits to its branch: each push needs a new approval and the code is checked under the proposed rules, but read what it changes before approving a commit Voxium did not write. Who counts as having asked for a file comes from git authorship, which whoever pushes can set: a Team Leader who writes a proposal file into a member's pull request under that member's name is not recognised. The same holds for ordinary pull requests, where a Team Leader can push to a member's pull request and approve it with a GitHub review.
* Opaque imports are only found, not followed. A variable that holds a module name is not looked up, and the unknown part of a name is taken to stay below the folder it starts with. A `..` or an empty part that is written behind it makes the name opaque. Not seen at all are code in strings (`eval`, `new Function`, worker scripts given by path), a module object that another function was given (`f(module)`), reflection (`Reflect`, `Function.prototype.caller`), `jest.mock` and `vi.mock`, imports in JSDoc comments, triple slash references, Nuxt auto imports, and `.svelte` and `.astro` files, `.mdx`, or Vue templates with other delimiters than `{{ }}`. A file of the tree that is not source code is opaque only where an import leads to it by its name, a name with unknown parts, a folder's `package.json` `main` or the config files above it. At most 1,000 opaque imports are listed for each file.
* The nesting limit leaves room for a cold parser on Node's default stack, also with 40% of it in use (150 nested parentheses, 123 nested calls, 422 nested conditionals, 565 nested `if` statements are read). A runtime with a much smaller stack can still refuse a file below it, as one that could not be read.
* The CLI follows symlinks within the project and reads submodules. A source file that is a symlink leading out of the project, or nowhere, counts as code that could not be read (exit 2), as on the platform. The platform does neither: a symlinked source or config file is an error there, imports through a symlinked folder or into a submodule are not seen, and a symlink without an ending that points to data is opaque there, because the platform cannot see where it points. The MCP tools do not know the paths of the tree, so there a file that is not source code, a committed `node_modules` folder and a config file that is not there are not seen.
* `public_api` is about files, not about what they export: an entry that re-exports an internal file makes that file public, and imports within a module are never judged. `naming` and `placement` see paths only.
* Without the platform, an exception that has already expired can be removed in a PR but not renewed without an admin override.
* Not built yet: API tokens for agents, remote MCP server on Workers, billing, ArchUnitTS test files, GitLab merge request comments, Queues for large repos.
* The platform has been verified with unit tests and in the local Workers runtime with a local D1. It has not been run against a real GitHub App yet.
